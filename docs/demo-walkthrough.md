# AI Review Cockpit 演示演讲稿

> 时长：约 10-12 分钟
> 形式：本地运行，浏览器演示

---

## 一、开场白（1 分钟）

**核心一句话：**
> 它不是把 diff 丢给大模型，而是围绕 Changed Lines、Evidence Chain 和 Confidence Gate 组织一次可解释、低噪声的 PR Review。

**展开说明：**
现有的 AI 代码审查工具大多是"diff-to-LLM"模式——把整个 PR diff 发给 AI，让 AI 列出一堆问题。但这样做有三个问题：
1. **翻旧账**——AI 会把旧代码的问题也算成新 PR 的问题
2. **不可解释**——你不知道 AI 为什么觉得这里有问题
3. **噪音多**——AI 给了一堆建议，你不知道哪些是真正重要的

AI Review Cockpit 的目标就是解决这三个问题。

---

## 二、创新点讲解（2 分钟）

### 核心概念 1：Changed Lines（只审变更行）
- 不是把整个 diff 丢给 LLM
- 先解析 unified diff，精确提取新增和修改行
- **效果**：不翻旧账，评审者只看本次改动

### 核心概念 2：Risk-Aware Routing（风险感知路由）
- 每个文件按路径模式、变更规模和关键词打分（-2 到 15）
- 低分文档 → 跳过；中等 → 普通分析；高分 → 深度分析 + 关联上下文
- **效果**：资源集中到高风险文件，不浪费在 README 上

### 核心概念 3：混合规则 + AI 引擎
- **15 条静态规则**（S001-S015）捕获确定性问题：硬编码密码、危险 SQL、空 catch、N+1 查询
- **AI** 处理规则无法理解的问题：空值检查缺失、事务风险、业务逻辑缺陷
- 两者同时命中 → 置信度加成
- **效果**：规则保证确定性，AI 覆盖灵活性

### 核心概念 4：Confidence Gate（置信度门禁）
- 三层阈值：
  - < 0.60 → 隐藏（低置信度噪声）
  - 0.60–0.79 → 仅报告可见
  - ≥ 0.80 → GitHub Ready（可推送评论）
- **效果**：评审者不会被低质量建议刷屏
- **对照实验**：驾驶舱报告展示"普通 diff-to-LLM"和"Cockpit 门控后"的对比

### 核心概念 5：Evidence Chain（证据链）
- 每条发现附带：来源（规则/AI）→ 代码片段 → 置信度原因
- **效果**：评审者 3 秒内判断"这条发现值不值得看"

## 三、演示步骤（5-6 分钟）

### Step 1：首页 —— 启动入口

**操作：** 打开浏览器访问 `http://localhost:8000`

**讲解要点：**
- 品牌名 AI Review Cockpit，副标题："基于证据链的 GitHub PR 智能评审工具"
- 核心说明：只分析 changed lines，结合 Static Rule、AI Review、Confidence Gate 和 Evidence Chain
- 表单：粘贴 PR 链接即可使用，Token 可选

**话术：**
> "首页非常简洁，核心就是输入 GitHub PR 链接。不填 Token 也能审公开 PR，系统会自动降级。右上角有运行状态面板，显示当前使用的模型和是否配置了密钥。"

### Step 2：提交一个真实 PR 审查

**操作：** 输入 `https://github.com/openclaw/openclaw/pull/88531`，点击"开始评审"

**讲解要点：**
- 点击后进入进度页，展示 7 阶段 Pipeline
- 阶段 1：FETCHING_PR — 获取 PR 元数据和 diff
- 阶段 2：BUILDING_CONTEXT — 构建文件上下文
- 阶段 3：STATIC_SCAN — 15 条规则扫描
- 阶段 4-6：AI 审查（摘要、逐文件、跨文件）
- 阶段 7：去重 + 置信度过滤

**话术：**
> "整个 Pipeline 从前到后大约跑 20-30 秒。注意阶段 3 是静态规则扫描，几毫秒就完成了；阶段 4-6 是 AI 审查，是主要耗时部分。阶段 7 会做去重和置信度门槛过滤，只有符合条件的结果才会展示给评审者。"

### Step 3：浏览驾驶舱报告

**操作：** 进入报告页

**讲解要点：**
- **指标卡**：风险等级、Review 置信度、发现项数量、合并建议
- **Pipeline 条**：原始输出 → 去重后 → 置信度过滤 → GitHub Ready，每一步的数字变化直观展示过滤效果
- **Cockpit Quality Gate 对照**：展示"普通 diff-to-LLM 全展示" vs "Cockpit 门控后"的对比
- **Review Decision**：给出明确的合并建议（暂不建议合并/修复后再合并/建议人工复核/可安全合并）
- **File Risk Map**：按文件展示风险分 + 分析深度，点击可筛选

**话术：**
> "报告页的核心是辅助 Reviewer 做合并决策，而不是扔给 Reviewer 一个长长的发现列表。顶部 4 个指标卡让你 3 秒内了解 PR 整体状况，中间 Pipeline 条展示从原始输出到最终可见的过滤链路，最下面是每条发现的详细证据。"

### Step 4：展开 Evidence Chain

**操作：** 点击一条严重等级高的发现，展开证据链

**讲解要点：**
- 展示：变更文件 → 行号 → 规则匹配/AI 来源 → 置信度评分
- 代码片段高亮显示
- 置信度原因说明

**话术：**
> "每条发现都附带完整的证据链。评审者不需要猜测为什么这里被标记了——直接看到哪条规则命中了、对应的代码是什么、置信度评分的原因是什么。这样就解决了普通 AI 审查的'黑箱'问题。"

### Step 5：GitHub 评论预览

**操作：** 点击"预览 GitHub 评论"

**讲解要点：**
- 展示生成的 Markdown 格式评论
- 只有 GitHub Ready 的发现项才会包含在内
- 支持 dry_run 模式，预览但不发送

**话术：**
> "高置信度的发现项可以自动回写到 PR 对话里。重复评审不会刷屏——系统会找到之前发的评论并更新。这里演示的是预览模式，不会真的发送。"

### Step 6：评测看板（可选，如果时间充裕）

**操作：** 导航到 /evaluation

**讲解要点：**
- Golden Evaluation：20 个合成用例 + 5 个真实 PR 回放
- 展示准确率、召回率、误报数、漏报数
- 规则级质量表格，逐规则展示命中情况
- 普通 diff-to-LLM 基线 vs Cockpit 置信门控的对照

**话术：**
> "我们不是'能不能审 PR'这种定性展示，而是用 20 个固定用例量化 Precision、Recall 和误报率。同时对比了普通 diff-to-LLM 基线和 Cockpit 门控后的效果——可以看到门控后无效输出减少多少。"

## 四、收尾总结（1 分钟）

**核心差异总结：**

| 维度 | 普通 AI Review | AI Review Cockpit |
|------|---------------|-------------------|
| 审查对象 | 整个 diff | 只分析 Changed Lines |
| 误报控制 | 无门控 | 三层 Confidence Gate |
| 可解释性 | 黑箱 | Evidence Chain 可追溯 |
| 确定性 | 全 AI | 15 条静态规则 + AI 混合 |
| 资源分配 | 每文件同等待遇 | Risk-Aware Routing |
| 效果度量 | 定性 Demo | 20 个用例量化评测 |

**一句话总结：**
> AI Review Cockpit 不是"把代码扔给 AI"，而是围绕 Changed Lines、Evidence Chain 和 Confidence Gate 构建了一套**可量化、可解释、低噪声**的 PR 评审工具。

## 五、Q&A 备选问题

**Q: 为什么不直接用 ChatGPT 审代码？**
A: ChatGPT 会把旧代码问题当成新 PR 的问题，而且没有置信度门控，很多建议质量不可控。我们只审 Changed Lines，用规则保证确定性，用门控过滤低质量结果。

**Q: 规则能自定义吗？**
A: 目前内置 15 条规则（S001-S015）。架构支持扩展，后续会开放自定义规则配置。

**Q: AI 产生的幻觉怎么控制？**
A: 两层控制：一是置信度评分，低分结果默认隐藏；二是 Evidence Chain，每条发现附带证据，评审者可以快速判断是否可信。

**Q: 支持私有仓库吗？**
A: 支持，配置 GitHub Token 即可。不配 Token 也能通过公开 diff 端点审查公开仓库。

**Q: 这个项目用了哪些技术？**
A: FastAPI + SQLAlchemy + SQLite + Jinja2 + Bootstrap，AI 通过 OpenAI 兼容接口调用（支持 Claude、DeepSeek、GPT 等），GitHub 集成使用 httpx。
