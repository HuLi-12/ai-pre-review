# AI PR Review 助手后续优化方案

本文档面向“题目三：AI PR Review 助手”的后续实现与答辩展示，目标是把当前项目从“可运行的 AI PR 审查 Demo”继续推进到“链路稳定、结果可量化、差异化明确、UI 可展示”的作品状态。

## 1. 当前基线

### 已具备能力

- 支持用户输入 GitHub PR URL，解析仓库、PR 编号并拉取 PR 元信息与文件变更。
- 支持公开 PR 的 `.diff` fallback，降低 GitHub API 权限或限流导致的失败概率。
- 已有静态规则扫描器，覆盖硬编码密钥、危险删除、N+1 查询、缺少测试、调试输出、Web 接口缺少鉴权或校验等风险。
- 已有 AI 审查链路：PR 总结、文件级审查、跨文件审查、结果合并去重。
- 已有置信度门控：低置信度结果不直接展示，高风险或高置信度结果才进入 GitHub 评论候选。
- 已有 golden evaluation：固定 8 个 diff 样例，初步量化误报、漏报和置信度门控效果。
- 后端已有 `/api/evaluation/golden`，首页与报告页已经可以展示评测概览。
- 模型不可用时有 fallback 输出，保证 Demo 不会因为缺少 API Key 直接崩溃。

### 主要不足

- Golden evaluation 规模仍偏小，更多是规则回归测试，还没有覆盖真实 PR 的复杂上下文。
- AI 输出质量还缺少独立评测，无法证明“AI 审查结果比普通 diff-to-LLM 更稳”。
- 上下文获取仍偏文件和 diff 级别，尚未形成调用关系、测试覆盖、配置影响、跨文件依赖的系统化上下文包。
- UI 已能展示基础报告，但“我们为什么比普通审查工具更好”的证据还不够突出。
- React 原型仍偏静态展示，和后端 API 的真实数据链路需要继续打通。
- GitHub 评论能力还可以更进一步：行级评论、重复评论去重、评论更新、仅发布高置信结果。
- 后台任务仍是进程内异步任务，不适合长时间运行和多用户并发。
- 数据库迁移、生产配置、错误状态、限流处理还需要增强。

## 2. 优化总目标

后续优化不只是“多加几个功能”，而是围绕三个核心问题推进：

1. 审得准：用 golden evaluation、真实 PR 回放、误报漏报统计证明审查结果可靠。
2. 审得快：通过上下文裁剪、缓存、并发、模型路由降低响应时间和成本。
3. 审得有特点：突出普通 diff-to-LLM 没有的置信度门控、规则与 AI 融合、风险分层、可解释证据链和反馈闭环。

## 4. 具体数据与指标设计

### Golden Evaluation 指标

- `precision`：系统指出的问题中有多少是真问题。
- `recall`：预期问题中有多少被系统发现。
- `false_positive_count`：误报数量。
- `false_negative_count`：漏报数量。
- `visible_rate`：经过可见阈值后仍展示的结果比例。
- `github_ready_rate`：达到 GitHub 评论阈值的结果比例。
- `confidence_avg`：平均置信度。
- `confidence_calibration`：高置信结果是否真的更准确。

### 真实 PR 运行指标

- `analysis_latency_p50` / `analysis_latency_p95`：分析耗时。
- `files_changed` / `files_analyzed` / `files_skipped`：文件覆盖情况。
- `tokens_input` / `tokens_output`：上下文与输出成本。
- `model_cost_estimate`：单次 PR 评审成本。
- `finding_count_by_severity`：不同严重级别问题数量。
- `comment_candidate_count`：可发布到 GitHub 的建议数量。
- `deduplicated_count`：去重减少的噪声数量。
- `reviewer_acceptance_rate`：人工标记为有用的比例。

### UI 展示指标

- 总体风险等级。
- 高风险文件 Top N。
- 规则命中分布。
- AI 建议数量与采纳状态。
- 普通 diff-to-LLM 对照结果。
- 置信度门控前后数量变化。
- 当前报告的上下文覆盖范围。

## 5. 推荐实现顺序

### 第一阶段：评测与报告可信度

1. 新增 `docs/evaluation-cases.md`，记录每个 golden case 的意图、预期 finding、误报控制点。
2. 把 golden cases 扩展到 20-30 个，并覆盖真实项目场景。
3. 新增真实公开 PR 回放集，保存 diff snapshot，避免评测依赖网络状态。
4. 后端输出 rule-level metrics，前端报告页展示 precision、recall、FP、FN。
5. 增加“普通 diff-to-LLM vs 本系统”的对照指标。

### 第二阶段：上下文与规则能力

1. 建立 Context Builder，把相关测试、配置、调用关系纳入 prompt。
2. 增加路径分类器：源码、测试、文档、生成文件、配置文件分别处理。
3. 对 Python / JavaScript / TypeScript 增加 AST 级规则，减少正则误报。
4. 为每条 finding 输出 evidence，包括文件、行号、代码片段、规则、置信度原因。
5. 对大 PR 增加裁剪策略和跳过说明。

### 第三阶段：UI 产品化

1. 将 React prototype 接入后端任务 API、报告 API、评测 API。
2. 新增 Evaluation 页面，专门展示评测集、指标、对照实验。
3. 报告页按风险优先排序，提供文件筛选、规则筛选、严重级别筛选。
4. 为每条建议提供“有用 / 误报 / 忽略 / 已修复”反馈入口。
5. 完成桌面端与移动端布局检查，避免卡片堆叠、文本溢出、按钮不可用。

### 第四阶段：GitHub 与工程化

1. 实现行级 GitHub 评论，带 fingerprint，重复运行时更新旧评论。
2. 将后台任务抽象为队列，后续可替换 Celery / RQ / Dramatiq。
3. 引入 Alembic 管理数据库升级。
4. 增加 GitHub rate limit 与模型调用失败的重试退避。
5. 补齐鉴权、token 加密存储、审计日志和部署文档。

## 6. 差异化表达

当前项目不能只讲“我们也能让 AI 看 diff”。答辩或展示时应强调以下差异：

1. 普通方案：把 PR diff 直接丢给 LLM，结果容易啰嗦、重复、误报高。
2. 本系统：先用静态规则识别确定性风险，再用 AI 做上下文解释和建议生成。
3. 普通方案：所有建议都展示，评审者需要自己过滤。
4. 本系统：用置信度门控控制噪声，只展示达到阈值的 finding，只评论高价值问题。
5. 普通方案：没有评测闭环，很难证明效果。
6. 本系统：内置 golden evaluation，可以量化 precision、recall、误报、漏报和门控效果。
7. 普通方案：只看当前 diff。
8. 本系统：后续加入调用关系、测试、配置、风险文件排序，形成更完整的上下文理解。
9. 普通方案：无法根据团队偏好变好。
10. 本系统：通过用户反馈、规则调参、阈值配置逐步适应团队代码审查习惯。

## 7. 验收标准

### 功能验收

- 输入公开 GitHub PR URL 后，能生成完整报告。
- 报告包含 PR 总结、风险文件、问题列表、建议动作、置信度和证据。
- 模型不可用时，系统仍能用静态规则生成基础报告。
- Golden evaluation 能在本地稳定运行，并输出结构化指标。
- UI 能展示评测结果和门控效果。
- 至少一个公开 PR 样例可以作为现场演示。

### 质量验收

- 后端测试全部通过。
- 前端 build 通过，lint 不存在阻断性错误。
- 主要 API 有错误状态和超时处理。
- 规则变更必须同步更新 golden evaluation。
- 高置信 finding 应尽量可解释，不能只给空泛建议。

### 展示验收

- 首页能说明工具解决什么问题，但不要变成纯营销页。
- 报告页第一屏展示风险结论和关键指标。
- Evaluation 页面展示本系统相对普通 diff-to-LLM 的噪声控制效果。
- 每条建议能看到“为什么判断为问题”和“应该怎么改”。
- UI 布局在常见桌面宽度下不拥挤，在移动端不重叠。

## 8. 建议下一步任务

建议下一步优先执行以下 5 个任务：

1. 扩展 golden evaluation 到 20-30 个案例，并为每个案例补充说明文档。
2. 新增真实公开 PR 回放集，固定 diff snapshot 和人工预期结果。
3. 把评测指标独立成 Evaluation UI 页面，展示规则级 precision / recall / FP / FN。
4. 报告页增加 finding evidence，包括规则来源、代码片段、置信度原因。
5. React prototype 接入真实后端 API，替换 mock 数据。

完成这 5 项后，项目会从“有 AI 审查功能”提升为“有可证明质量控制的 AI PR Review 工具”，更符合题目中对分析准确性、上下文理解、误报漏报控制、响应速度和使用体验的要求。
